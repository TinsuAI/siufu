# Story 3.6: Declaration Review Form

## Status
Done

## Story
**As a** user,
**I want** to see all extracted declaration data in an editable form with confidence indicators,
**so that** I can review and correct any errors before approval (per FR10, FR11, FR12).

## Acceptance Criteria
1. Review screen (`/declarations/[id]/review`) displays extracted data in structured form sections: Company Information, Shipment Details, Product Line Items, Tax Calculations
2. Each field color-coded by confidence: Green (>90%), Yellow (70-90%), Red (<70%) per FR11
3. All fields editable inline using React Hook Form with Zod validation
4. Auto-save functionality: Save changes to backend every 5 seconds (per NFR7)
5. Visual indicator showing "Saving..." vs "Saved" status
6. Validation errors display inline (e.g., "HS Code must be 8 digits")
7. Product line items displayed in table format with add/remove row functionality
8. Cross-document validation warnings displayed prominently (e.g., "Warning: Invoice total ($23,208) does not match CO total ($23,200)")
9. Form data fetched from `GET /api/declarations/{id}` on page load
10. Updates sent to `PATCH /api/declarations/{id}` on auto-save or manual save

### Data Models
**[Source: architecture/data-models.md]**

**Declaration Interface:**
```typescript
export interface Declaration {
  id: string;
  status: DeclarationStatus;
  uploaded_files: UploadedFile[];
  extracted_data: Record<string, any> | null;
  draft_data: DraftData | null;  // This is what the form edits
  validation_warnings: ValidationWarning[];
  confidence_scores: Record<string, number>;  // e.g., {"company.name": 0.95, "products.0.hs_code": 0.68}
  processing_progress: number;
  processing_error: string | null;
  // ... other fields
}
```

**DraftData Structure (JSONB flexible schema):**
The `draft_data` field contains user-editable declaration data organized into sections:
- **Company Information**: importer name, tax ID, address, contact
- **Shipment Details**: BOL number, arrival date, port, containers
- **Product Line Items**: array of products with description, HS code, quantity, unit price, origin
- **Tax Calculations**: VAT rate, import duty rate, total tax amount

**ValidationWarning Interface:**
```typescript
export interface ValidationWarning {
  message: string;
  severity: 'error' | 'warning';
  field?: string;  // Optional field reference
}
```

### API Specifications
**[Source: architecture/api-specification.md]**

**Fetch Declaration Data:**
- Endpoint: `GET /api/declarations/{id}`
- Returns: Full `Declaration` object with all fields
- Auth: JWT Bearer token required
- Use OpenAPI-generated client: `apiClient.getDeclaration(id)`

**Update Draft Data (Auto-Save):**
- Endpoint: `PATCH /api/declarations/{id}`
- Body: Partial update to `draft_data` field (nested merge strategy)
- Returns: Updated `Declaration` object
- Auth: JWT Bearer token required
- Backend merges partial updates: `merged_data = {...existing_data, ...new_data}`
- Use OpenAPI-generated client: `apiClient.patchDeclaration(id, patchData)`

**Note:** The backend automatically tracks corrections when `draft_data` is updated. See Epic 4.1 for correction tracking implementation.

### Component Specifications

**State Management Pattern:**
- Use TanStack Query for server state (declaration data, mutations)
- Use React Hook Form for local form state
- Do NOT store form data in Zustand - let React Hook Form manage it
- Zustand only for UI state like: collapsed sections, filter preferences

**TanStack Query Pattern:**
```typescript
// Example from architecture/frontend-architecture.md
export function useDeclaration(id: string) {
  const query = useQuery({
    queryKey: ['declarations', id],
    queryFn: () => apiClient.getDeclaration(id),
    refetchInterval: (data) => {
      // Poll every 2s if processing (for status updates)
      if (data?.status === 'PROCESSING') return 2000;
      return false;
    },
  });
  // ... mutations
}
```
