### Architecture Context

**Note:** No architecture documents found at `docs/architecture/`. The following technical decisions are based on PRD requirements (docs/prd.md):

#### Tech Stack (from PRD)
- **Framework:** Next.js 15.5.6 with App Router
- **Language:** TypeScript 5.6 (strict mode)
- **Styling:** Tailwind CSS 4.0 + shadcn/ui component library
- **State Management:**
  - Zustand (client state) - for auth, UI state
  - TanStack Query (server state/caching) - for API data fetching
- **Backend API:** FastAPI at http://localhost:8000/api
- **Port:** Frontend runs on port 3000

#### Design System Requirements (from PRD)

**Primary Colors:**
- Navy Blue (slate-700): Trust, professional, headers
- Green (emerald-500): Success, high confidence (>90%)
- Amber (amber-500): Warning, medium confidence (70-90%)
- Red (rose-500): Error, low confidence (<70%)

**Typography:** Clean sans-serif (Inter or system font stack)

**Layout:** Desktop-first design (NOT mobile-first)
- Primary viewport: 1920x1080
- Minimum supported: 1366x768

### Important Notes for Dev Agent

1. **DO NOT implement authentication logic** - Story 3.1 only sets up the structure. Auth implementation is Story 3.2.

2. **Placeholder pages are OK** - Routes like `/login`, `/upload`, etc. should be simple placeholder pages with headings. Full implementation comes in later stories.

3. **Desktop-first design** - This is a B2B tool for power users. DO NOT optimize for mobile. Minimum width: 1366px.

4. **Use httpOnly cookies for auth** - Do NOT store JWT tokens in localStorage. Cookie handling will be implemented in Story 3.2.

5. **shadcn/ui is the ONLY component library** - Do NOT use Material-UI, Ant Design, or any other library. All UI components must come from shadcn/ui.

6. **TanStack Query for ALL API calls** - Do not use raw fetch/axios for data fetching in components. Use TanStack Query hooks.

7. **Tailwind CSS ONLY** - No CSS modules, styled-components, or other styling solutions.

8. **Health check is simple** - Just fetch `/api/health` and display status. No complex error handling needed for this story.

### Testing

#### Testing Standards
**Test Framework:** Vitest 2.1 with React Testing Library 16.1

**Test File Locations:**
- Unit tests: `frontend/src/__tests__/unit/`
- Component tests: Co-located with components or in `__tests__/unit/components/`
- Integration tests: `frontend/src/__tests__/integration/`

**Required Tests for Story 3.1:**
1. **Auth Store Test:** Test Zustand store actions (login, logout, state updates)
2. **Header Component Test:** Test navigation links render, user menu displays
3. **Route Test:** Verify all defined routes are accessible

**Test Patterns:**
- Use React Testing Library for component tests
- Mock API calls with Mock Service Worker (msw)
- Test user interactions, not implementation details
- Aim for 60%+ coverage on new code

**Example Test Structure:**
```typescript
// src/__tests__/unit/stores/auth-store.test.ts
import { describe, it, expect } from 'vitest';
import { useAuthStore } from '@/stores/auth-store';

describe('Auth Store', () => {
  it('should initialize with no user', () => {
    const state = useAuthStore.getState();
    expect(state.user).toBeNull();
  });

  it('should set user on login', () => {
    const { login } = useAuthStore.getState();
    login({ id: '1', email: 'test@example.com', name: 'Test User' });
    expect(useAuthStore.getState().user).toBeTruthy();
  });
});
```
