### Backend Testing Patterns
[Source: architecture/backend-architecture.md]

**Repository Pattern Testing:**
- Use async fixtures for database session
- Test repository methods with TestClient
- Mock external API calls in unit tests
- Use separate test database with automatic cleanup

**Celery Task Testing:**
- Mock Celery tasks in unit tests
- Use `asyncio.run()` to test async task functions
- Verify task state transitions (PENDING → PROCESSING → COMPLETED)
- Mock external services (OCR, LLM) to avoid costs

**Example Test Pattern:**
```python
# backend/tests/unit/test_user_model.py
async def test_user_creation(db_session):
    user = User(email="test@example.com")
    db_session.add(user)
    await db_session.commit()
    assert user.id is not None
```

### Frontend Testing Patterns
[Source: architecture/frontend-architecture.md]

**Component Testing with React Testing Library:**
- Use `render()` from test-utils with providers
- Test user interactions with `userEvent`
- Assert on accessible queries (getByRole, getByLabelText)
- Mock API calls with MSW

**TanStack Query Hook Testing:**
- Wrap hooks in QueryClientProvider
- Mock API responses using MSW handlers
- Test loading, success, and error states
- Verify cache invalidation and refetch behavior

**Example Test Pattern:**
```typescript
// frontend/src/__tests__/unit/declaration-form.test.tsx
import { render, screen } from '@testing-library/react';
import { DeclarationForm } from '@/components/declarations/declaration-form';

test('renders form with all fields', () => {
  render(<DeclarationForm />);
  expect(screen.getByLabelText('Importer Name')).toBeInTheDocument();
});
```

### Playwright MCP Integration
[Source: Epic Details AC 20-21, 31-33]

**MCP Configuration:**
- MCP server accesses codebase context (component selectors, API endpoints, user flows)
- AI-assisted test generation based on user stories and component structure
- Generated tests validated against manual test baseline for accuracy

**MCP Test Generation Workflow:**
1. MCP queries codebase for component selectors (e.g., `data-testid` attributes)
2. MCP identifies API endpoints from backend routes
3. MCP generates test script using Playwright API
4. Developer reviews and validates generated test
5. Generated test added to E2E test suite

**Example MCP Usage:**
- Input: User story "Login → Upload → Review"
- MCP Output: Generated `happy-path.spec.ts` with selectors and assertions
- Developer validates test passes and matches expected behavior

### Coding Standards - Testing
[Source: architecture/coding-standards.md]

**Naming Conventions:**
- Test files: `test_*.py` (backend), `*.test.tsx` (frontend)
- Test functions: `test_*` (pytest), `test('description', ...)` (Vitest)
- Mock fixtures: `mock_*_response` (both)

**Type Safety:**
- Backend: Use type hints in test functions
- Frontend: Use TypeScript for all test files
- Zod schemas: Share validation between tests and implementation

**API Testing:**
- Never use direct `fetch()` in tests
- Use generated API client or mock with MSW
- Test error handling with invalid inputs

### Environment Variables for Testing
[Source: architecture/coding-standards.md]

**Backend Test Environment:**
- `DATABASE_URL_TEST`: Separate PostgreSQL test database
- `GOOGLE_CLOUD_KEY_TEST`: Mock service account key (not real API key)
- `OPENROUTER_API_KEY_TEST`: Mock API key for tests

**Frontend Test Environment:**
- `NEXT_PUBLIC_API_URL_TEST`: Backend API URL for E2E tests (http://localhost:8000)
