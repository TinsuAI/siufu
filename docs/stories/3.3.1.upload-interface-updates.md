# Story 3.3.1: Upload Interface Updates

## Status
**Done**

## Story
**As a** user,
**I want** a streamlined file upload interface with multi-file C/O support,
**so that** I can efficiently upload only the essential documents without unnecessary file requirements.

## Acceptance Criteria
1. Upload screen (`/upload`) displays 4 file upload zones: Arrival Notice (PDF), Bill of Lading (PDF), Certificate of Origin (PDF - multiple files), Invoice (PDF/Image)
2. Removed: Good List (Excel) and EXIM Tariff (Excel) upload zones (no longer required)
3. Certificate of Origin (C/O) zone supports **multiple file uploads** (drag-and-drop multiple files or select multiple via file browser)
4. C/O zone displays all uploaded C/O files with individual remove buttons for each
5. Drag-and-drop functionality works for all drop zones with visual feedback (highlight on drag-over)
6. Alternative: Click to open file browser for each zone (with multi-select enabled for C/O)
7. Visual checklist shows which files uploaded:
   - ✓ green checkmark for AN, BOL, Invoice when file added
   - ✓ green checkmark for C/O when at least 1 file added, with count badge showing number of files (e.g., "3 files")
8. File type validation on frontend before upload (show error if wrong type)
9. File size validation (PDFs max 10MB, images max 5MB) with clear error messages
10. "Process Declaration" button enabled only when required files uploaded:
    - AN: 1 file
    - BOL: 1 file
    - C/O: At least 1 file (no upper limit, but reasonable UX limit of 10 files with warning)
    - Invoice: 1 file
11. Clicking "Process Declaration" uploads files to updated `POST /api/declarations/upload` endpoint and triggers processing
12. After upload, user redirected to processing status screen showing declaration ID
13. Error handling: Display clear messages if upload fails (network error, validation error)

## Dev Notes

### Business Context & Architectural Decision

**CONFIRMED - Architectural Decision:**

This story removes Good List and EXIM Tariff from per-declaration uploads based on the architectural pattern established in Epic 2 and Epic 4:

- **Story 1.6 (File Upload)**: Originally specified 6 files per declaration including Good List and EXIM Tariff
- **Story 2.1 (Knowledge Base Import)**: Imports Good List/EXIM Tariff as **system-wide knowledge bases** from `resources/goodlist1.xls`, `resources/goodlist2.xls`, `resources/EXIM-Tarrif.xlsx`
- **Story 4.3 (Knowledge Base Management)**: Provides admin UI to upload updated Good List/EXIM Tariff files (system-wide, not per-declaration)
- **API Specification**: Separate endpoints: `POST /api/knowledge-base/good-list/upload` (system-wide) vs `POST /api/declarations/upload` (per-declaration)

**Architectural Decision:**
Good List and EXIM Tariff are **system-wide knowledge bases** managed by administrators (Story 4.3), NOT files uploaded with each declaration. The original Story 1.6 and 3.3 specifications were inconsistent with this architecture.

**Reason for This Change:**
- **Eliminates redundancy**: Users don't need to upload the same Good List/Tariff files with every declaration
- **Centralizes knowledge**: Admins manage one authoritative Good List/Tariff database (Story 4.3)
- **Aligns with Epic 2**: Story 2.2 (Fuzzy Matching) queries system-wide Good List database, not per-declaration files
- **Aligns with Epic 4**: Story 4.3 provides version control for knowledge base files

**Impact on Related Stories:**
- ✅ **Story 2.2 (Fuzzy Matching)**: No impact - queries system-wide `good_list_entries` table
- ✅ **Story 2.4 (Tariff Lookup)**: No impact - queries system-wide `tariff_rates` table
- ✅ **Story 4.3 (Knowledge Base Upload)**: Confirms this is the correct approach
- ⚠️ **Story 3.5 (PDF Viewer)**: Update to handle only 4 PDFs (AN, BOL, CO, INVOICE) - no longer needs Good List/Tariff viewer

**Decision Rationale Confirmed:**
This architectural approach has been validated and approved. Good List and EXIM Tariff will be managed as system-wide knowledge bases by administrators, not uploaded per-declaration. This reduces user effort, maintains data consistency, and aligns with the platform's learning and knowledge management architecture.


**Backend validation updates:**
- Check for 4 file types (AN, BOL, CO array, INVOICE)

### Security Considerations

**File Upload Security:**
1. **MIME Type Validation**:
   - Frontend: Check file extensions (.pdf, .jpg, .png)
   - Backend: Use `python-magic` to verify actual file type (prevent extension spoofing)

2. **File Size Limits**:
   - Per-file: PDFs ≤ 10MB, Images ≤ 5MB
   - Total upload: ≤ 100MB across all files
   - Enforce on both frontend (UX) and backend (security)

3. **DoS Protection**:
   - Hard limit: Max 20 C/O files (reject with HTTP 400)
   - Rate limiting: Max 10 uploads per user per hour
   - Timeout: 60 seconds for complete upload

4. **CSRF Protection**:
   - CSRF token required for POST /api/declarations/upload
   - httpOnly cookies for authentication (already implemented in Story 3.2)

5. **Malware Scanning** (Future Enhancement):
   - Consider integrating ClamAV for uploaded files
   - Not required for MVP but document as Phase 2 enhancement

**Input Validation:**
- Sanitize filenames (remove path traversal attempts: `../../etc/passwd`)
- Validate file paths before storage (prevent directory traversal)
- Validate JSON structure in uploaded_files JSONB field

### Backwards Compatibility

**Handling Existing Declarations:**

The JSONB `uploaded_files` field supports both old (6-file) and new (4-file) formats without migration:

```typescript
// Frontend detection logic:
function isOldFormat(uploadedFiles: any): boolean {
  return 'GOODLIST' in uploadedFiles || 'TARIFF' in uploadedFiles;
}

// Render upload page:
if (isOldFormat(declaration.uploaded_files)) {
  // Show read-only view: "Declaration created with old format (6 files)"
  // Display all 6 files including Good List and EXIM Tariff
} else {
  // Show new 4-file format with multi-C/O support
}
```

**Migration Strategy:**
1. **No database migration needed** - JSONB is schema-flexible
2. **Old declarations** (status: APPROVED, REJECTED) remain accessible in read-only mode
3. **In-progress declarations** (status: UPLOADED, PROCESSING) created before this change:
   - If user tries to edit: Show message "Please create a new declaration with updated upload interface"
   - Soft-delete old draft and redirect to new upload page
4. **Story 3.5 (PDF Viewer)** must handle both 4 PDFs (new) and 6 files (old) when displaying archived declarations

**No user data loss** - all historical declarations remain accessible.
