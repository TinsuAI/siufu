# Story 1.7.1: LLM Extraction Results Validation Against Expected Results

## Status
Ready for Review (Implementation Complete - 2025-10-27)

## Story

**As a** QA engineer and developer,
**I want** to validate LLM extraction results.json against manually-curated expected-results.json files,
**so that** I can verify extraction accuracy and generate visual validation reports highlighting discrepancies.

## Context

**SPRINT CHANGE (2025-10-27):** This story was originally scoped to extract validation data FROM CD.xlsx. That approach was incorrect - CD.xlsx is the **OUTPUT** (generated in Story 2.5), not the ground truth source.

**NEW APPROACH:** The user manually created `expected-results.json` files in each sample folder (1, 2, 3) as the TRUE ground truth for what a complete customs declaration should contain.

**KEY DISCOVERY:**
- `expected-results.json`: Manually curated ground truth (camelCase schema)
- `results.json`: LLM extraction output (snake_case schema)
- **Schema mismatch**: Requires on-the-fly translation during validation
- **Goal**: Generate visual markdown validation reports showing field-by-field comparison

**Previous Approach (DEPRECATED):**
- Attempted to extract from CD.xlsx using `validate_sample.py --generate-reference`
- This was fundamentally wrong - CD.xlsx is output, not input
- Old script archived as `validate_sample_cd_xlsx.py` for Story 2.5 reference

## Acceptance Criteria

1. **Load Expected Results**: Script loads expected-results.json from sample folder
   - Handles camelCase field names (declarationHeader, billOfLadingNumbers, etc.)
   - Validates JSON structure before comparison
   - Gracefully handles missing expected-results.json (error message)

2. **Load Extraction Results**: Script loads results.json from sample folder
   - Handles snake_case field names (declaration_header, bill_of_lading_number, etc.)
   - Extracts from nested "extracted_data" field if present
   - Validates JSON structure before comparison

3. **Schema Translation**: Automatically translates between camelCase and snake_case
   - Mapping: declarationHeader ↔ declaration_header
   - Mapping: billOfLadingNumbers ↔ bill_of_lading_number
   - Handles nested structures (importer.code ↔ importer.tax_code)
   - Documents all field mappings in code comments

4. **Field-by-Field Comparison**: Compares all fields with appropriate matching strategies
   - **Exact match**: IDs, codes (HS codes, tax codes, country codes)
   - **Fuzzy match (85% threshold)**: Text fields (names, addresses, descriptions)
   - **Numeric tolerance (±0.01%)**: Currency amounts, quantities
   - **Date format handling**: Handles DD/MM/YYYY format variations

5. **Visual Markdown Report Generation**: Generates comprehensive validation report
   - Saved to: resources/sample/{N}/validation-report-{timestamp}.md
   - **Report Structure:**
     - Summary: Total fields, matches, mismatches, missing
     - Color-coded results: ✅ PASS (green), ⚠️ PARTIAL (yellow), ❌ FAIL (red), 🔴 MISSING, ➕ EXTRA
     - Detailed field comparison table: Field Name | Expected | Actual | Status
     - Categorized by section (Declaration Header, Importer, Products, etc.)
     - Missing fields section (in expected but not in results)
     - Extra fields section (in results but not in expected)

6. **Validation Statistics**: Report includes accuracy metrics
   - Overall accuracy percentage
   - Accuracy by category (header, importer, products, etc.)
   - Critical field accuracy (must be 100%)
   - Important field accuracy (target 90%+)

7. **Sample Coverage**: Successfully validates all 3 samples
   - Sample 1: Generate validation-report.md
   - Sample 2: Generate validation-report.md
   - Sample 3: Generate validation-report.md
   - Each report clearly identifies missing/incorrect fields

8. **Error Handling**: Gracefully handles validation edge cases
   - Missing expected-results.json: Clear error message
   - Missing results.json: Clear error message
   - Schema mismatch (extra fields): Log warnings, continue
   - Null values: Treat as "missing" (acceptable if field is optional)

9. **CLI Interface**: Validation script has user-friendly CLI
   - Usage: `python3 validate_extraction_results.py <sample_folder_path>`
   - Example: `python3 validate_extraction_results.py ../resources/sample/1`
   - Output: Prints summary to console + saves full report as markdown
   - Exit code: 0 if validation passes, 1 if critical fields fail

10. **Documentation**: Complete validation guide
    - Create docs/qa/validation-guide.md with new workflow
    - Document field mapping (camelCase ↔ snake_case)
    - Provide examples of interpreting validation reports
    - Troubleshooting common validation issues

### Field Mapping Challenge

The main challenge is schema structure mismatch:

**expected-results.json structure:**
```json
{
  "declarationHeader": {
    "importer": {
      "code": "0104118221",
      "name": "..."
    },
    "transportDetails": {
      "billOfLadingNumbers": ["..."]
    }
  }
}
```

**results.json structure:**
```json
{
  "importer": {
    "tax_code": "0104118221",
    "name": "..."
  },
  "shipping_transport": {
    "bill_of_lading_number": "..."
  }
}
```

**Solution Approaches:**
1. **Option A (Recommended):** Flatten expected-results.json structure before comparison
   - Remove `declarationHeader` wrapper
   - Simplest approach, minimal code changes
2. **Option B:** Update FIELD_MAPPING to handle all nested paths
   - More complex mapping logic required
   - May need recursive path resolution
