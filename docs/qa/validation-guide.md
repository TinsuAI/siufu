# LLM Extraction Results Validation Guide

## Overview

This guide explains how to validate LLM extraction results against manually-curated ground truth data using the validation tooling developed in Story 1.7.1.

**Purpose**: Verify that the LLM correctly extracted customs declaration data from source documents (AN.pdf, BOL.pdf, CO.pdf, INVOICE.jpg) by comparing against expected values.

**Validation Approach**:
- **Ground Truth**: `expected-results.json` files manually created in each sample folder
- **LLM Output**: `results.json` files generated by the extraction pipeline
- **Comparison**: Field-by-field validation with appropriate matching strategies
- **Output**: Visual markdown reports highlighting discrepancies

**Location**: `resources/sample/{1,2,3}/expected-results.json`

**Source**: Manually curated by inspecting source PDF/JPG documents

**Schema**: camelCase field names with nested `declarationHeader` wrapper

**Structure**:

```json
        ...
      },
      "transportDetails": {
        "billOfLadingNumbers": ["130925EGLV 146500902564"],
        ...
      },
      ...
    },
    "items": [
      {
        "itemNumber": "01",
        "hsCode": "96190014",
        ...
      }
    ]
  }
]
```

**Purpose**: Represents what a complete, accurate customs declaration should contain

### results.json (LLM Output)

**Location**: `resources/sample/{1,2,3}/results.json`

**Source**: Generated by LLM extraction pipeline (Story 1.7)

**Schema**: snake_case field names, flat structure with `extracted_data` wrapper

**Structure**:
```json
{
  "id": "05d7f06c-9659-4d3d-8097-89096db940ad",
  "status": "READY_FOR_REVIEW",
  "extracted_data": {
    "declaration_header": {
      "declaration_number": null,
      ...
    },
    "importer": {
      "tax_code": "0104118221",
      "name": "CONG TY TNHH SAN XUAT DỊCH VỤ VÀ THUONG MAI THINH LINH",
      ...
    },
    "shipping_transport": {
      "bill_of_lading_number": "EGLV146500902564",
      ...
    },
    "products": [
      {
        "hs_code": "96190014",
        ...
      }
    ],
    ...
  }
}
```

**Purpose**: Represents what the LLM actually extracted from the documents

## Schema Translation

The validation script automatically handles schema differences between expected and actual results:

### 1. Structure Flattening

**expected-results.json** has a `declarationHeader` wrapper:
```json
{
  "declarationHeader": {
    "importer": {...},
    "transportDetails": {...}
  },
  "items": [...]
}
```

**Flattened to**:
```json
{
  "importer": {...},
  "transportDetails": {...},
  "products": [...]  // items → products
}
```

### 2. Field Name Translation

| Expected (camelCase) | Actual (snake_case) | Location |
|---------------------|---------------------|----------|
| `importer.code` | `importer.tax_code` | FIELD_MAPPING |
| `transportDetails.billOfLadingNumbers` | `shipping_transport.bill_of_lading_number` | FIELD_MAPPING |
| `transportDetails.quantityPackages` | `package_container.total_packages` | FIELD_MAPPING |
| `invoiceDetails.invoiceNumber` | `invoice.invoice_number` | Auto snake_case |
| `certificateOfOrigin.number` | `certificate_of_origin.co_number` | FIELD_MAPPING |

**Full mapping**: See `backend/validate_extraction_results.py` lines 38-125 (FIELD_MAPPING constant)

### 3. Array Renaming

- `items` (expected) → `products` (actual)
- Handled automatically by validation script

### Status Indicators

#### ✅ PASS (Green)
- **Meaning**: Field matches exactly or within acceptable tolerance
- **Criteria**:
  - Exact match for codes/IDs
  - Fuzzy match ≥85% for text fields
  - Numeric tolerance ±0.01% for amounts
- **Example**: `importer.code` expected "0104118221" → got "0104118221" ✅

#### ⚠️ PARTIAL (Yellow)
- **Meaning**: Field partially matches but below PASS threshold
- **Criteria**:
  - Fuzzy match 70-85% for text fields
  - Numeric tolerance 0.01-5% for amounts
- **Example**: Text field similarity 78% (below 85% threshold)

#### ❌ FAIL (Red)
- **Meaning**: Field does not match expected value
- **Criteria**:
  - Exact match failed for codes
  - Fuzzy match <70% for text
  - Numeric tolerance >5% for amounts
- **Example**: `importer.phone` expected "+24" → got "+84968893359" ❌

#### 🔴 MISSING
- **Meaning**: Field exists in expected-results.json but not extracted by LLM
- **Interpretation**: LLM failed to extract this field from source documents
- **Action**: Review source documents to confirm if field is present
- **Example**: `products[0].description` expected "Bỉm quần..." → got None 🔴

#### ➕ EXTRA
- **Meaning**: Field exists in results.json but not in expected-results.json
- **Interpretation**: LLM extracted additional field (may be calculated/derived)
- **Action**: Review if field is useful; may not be in ground truth
- **Example**: `confidence_scores.*` fields (not in expected data)

## Field Comparison Strategies

### 1. Exact Match (Codes, IDs, Numbers)

**Used for**:
- HS codes
- Tax codes
- Declaration numbers
- Invoice numbers
- Country codes

**Logic**:
```python
if expected_val == actual_val:
    status = "PASS"
```

**Example**:
- `importer.tax_code`: "0104118221" == "0104118221" → ✅ PASS

### 2. Fuzzy Match (Text Fields)

**Used for**:
- Names (importer, exporter, product descriptions)
- Addresses
- Product descriptions

**Threshold**: 85% similarity

**Logic**:
```python
similarity = SequenceMatcher(expected, actual).ratio()
if similarity >= 0.85:
    status = "PASS"
elif similarity >= 0.70:
    status = "PARTIAL"
else:
    status = "FAIL"
```

**Example**:
- Expected: "Công ty TNHH sản xuất..."
- Actual: "CONG TY TNHH SAN XUAT..."
- Similarity: 87% → ✅ PASS

### 3. Numeric Tolerance (Amounts, Quantities)

**Used for**:
- Invoice amounts
- Quantities
- Weights
- Tax amounts
- Exchange rates

**Tolerance**: ±0.01% (1 basis point)

**Logic**:
```python
diff_percent = abs(actual - expected) / expected
if diff_percent <= 0.0001:
    status = "PASS"
elif diff_percent <= 0.05:
    status = "PARTIAL"
else:
    status = "FAIL"
```

**Example**:
- Expected: 23208.80
- Actual: 23208.8
- Difference: 0% → ✅ PASS

### 4. Null Value Handling

**Both null**: ✅ PASS (acceptable for optional fields)
**Expected null, actual has value**: ✅ PASS (bonus extraction)
**Expected has value, actual null**: 🔴 MISSING (field not extracted)

## Common Validation Issues

### Issue 1: High MISSING Count

**Symptom**: >50% of fields marked as MISSING

**Likely Causes**:
1. Schema mismatch - field mapping incorrect
2. LLM prompt missing field extraction instructions
3. Source documents don't contain the data
4. OCR failed to extract text from documents

**Troubleshooting**:
```bash
# Check if declarationHeader flattening is working
python3 -c "
import json
from pathlib import Path
data = json.load(open('../resources/sample/1/expected-results.json'))[0]
print('Has declarationHeader wrapper:', 'declarationHeader' in data)
"

# Check field mapping coverage
grep "transportDetails\." backend/validate_extraction_results.py
```

**Resolution**: Review and update FIELD_MAPPING in `validate_extraction_results.py`

### Issue 2: Low Accuracy on Text Fields

**Symptom**: Many ⚠️ PARTIAL or ❌ FAIL for names/descriptions

**Likely Causes**:
1. Case sensitivity differences (uppercase vs lowercase)
2. Special characters stripped
3. Vietnamese characters encoding issues
4. Spacing differences

**Example**:
- Expected: "Công ty TNHH"
- Actual: "CONG TY TNHH"

**Resolution**: Fuzzy matching handles this - verify threshold is appropriate (85%)

### Issue 3: Numeric Mismatches

**Symptom**: ❌ FAIL for amounts that appear similar

**Likely Causes**:
1. Rounding differences
2. Currency conversion errors
3. Decimal separator issues (period vs comma)
4. Formatting differences (spaces in numbers)

**Example**:
- Expected: 16844.4
- Actual: 16844.40

**Resolution**: Use numeric tolerance matching (already implemented)

### Issue 4: Array Length Mismatch

**Symptom**: MISSING fields for `products[1].*` when only 1 product extracted

**Likely Cause**: LLM extracted fewer products than expected

**Resolution**: Review source documents - verify how many products exist

## Integration with CI/CD

### Automated Validation in Tests

The validation logic is integrated into integration tests:

**File**: `backend/tests/integration/test_end_to_end_processing.py`

**Test Flow**:
1. Upload sample files
2. Trigger processing
3. Poll for completion
4. Load expected-results.json for sample
5. Validate critical/important/calculated fields
6. Assert accuracy thresholds

**Running Tests**:
```bash
cd backend
pytest tests/integration/test_end_to_end_processing.py -v
```

### Continuous Validation

Add to CI pipeline:

```yaml
# .github/workflows/validation.yml
name: Validation
on: [push]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Validate Sample 1
        run: |
          cd backend
          python3 validate_extraction_results.py ../resources/sample/1
          # Check accuracy threshold
          accuracy=$(grep "Overall Accuracy" ../resources/sample/1/validation-report-*.md | tail -1 | grep -oP '\d+\.\d+')
          if (( $(echo "$accuracy < 30.0" | bc -l) )); then
            echo "❌ Sample 1 accuracy below 30% threshold"
            exit 1
          fi
```

## Troubleshooting

### Script Fails to Run

**Error**: `FileNotFoundError: Expected results file not found`

**Solution**: Ensure expected-results.json exists in sample folder

```bash
ls -la resources/sample/1/expected-results.json
```

### Report Not Generated

**Error**: No validation-report-*.md file created

**Solution**: Check script output for errors

```bash
python3 validate_extraction_results.py ../resources/sample/1 2>&1 | tee validation.log
```

### Schema Mismatch Warnings

**Warning**: Many fields mapped to null

**Solution**: Review FIELD_MAPPING in script, ensure expected field names match
